# hifi-wifi v3.1.0-beta.1: Measured Bufferbloat Control

**Public Beta** • October 2026

> [!NOTE]
> **This is a beta. Please measure it on your network and tell us what you see.**
> Run `sudo hifi-wifi bench --ab` (it tests with hifi-wifi off, then on) and post the output
> with `hifi-wifi doctor` and your device / router in a GitHub issue. Everything below that
> says "simulation" was measured in network namespaces, not on real Wi-Fi.
>
> To undo everything instantly: `sudo hifi-wifi off`. A reboot also clears all shaping.

v3.0 made Wi-Fi on handhelds reliable: power save, scan suppression, roaming, band steering.
v3.1 goes after the thing that actually makes games and streams stutter on a busy network:
**latency under load**, also called bufferbloat. When anything saturates your connection (a
Steam update, a cloud backup, someone else streaming), a queue fills up in your modem or
router and every packet waits behind it. Pings go from 20 ms to 200 ms. No Wi-Fi tweak
fixes that, because the queue is not on your device.

v3.1 moves the queue onto your device, keeps it short, and **measures** whether it worked.

---

## What's new

### 1. Autorate: bufferbloat control that finds your bottleneck by itself

The CAKE shaper only helps if its rate sits just below the real bottleneck. v3.0 guessed
that rate from the Wi-Fi link speed, which is usually far above your internet speed, so the
shaper rarely did anything (and it was off by default). Asking users to type in their ISP
speeds does not work either: they do not know them, and the real capacity changes.

Autorate measures instead, using the method of
[cake-autorate](https://github.com/lynxthecat/cake-autorate) from the OpenWrt community:

- It pings three public DNS resolvers and tracks each one's normal latency.
- When latency rises by more than 15 ms on at least half of them **while this device is
  pushing traffic close to its own recent peak**, the queue is ours: it lowers that
  direction to 90% of what was actually getting through.
- While the shaper is full and latency stays clean, it raises the rate again, quickly back
  to the last known-good point, then carefully above it.
- If another device on your network causes the bloat, autorate does **not** cut your rate.
  That would slow you down without fixing anything.
- By default it only shapes while the link is busy and removes itself after 60 s idle, so
  normal use and battery life are unaffected.
- Learned rates are remembered per Wi-Fi network, so the next session starts at the right
  place.

Watch it live: `sudo hifi-wifi off && sudo hifi-wifi autorate`, then start a download.

**Simulation with CAKE** (network namespaces on a GitHub Actions runner, reproducible with
`scripts/sim-bufferbloat.sh`: 20 Mbit bottleneck with a 400 ms buffer, 20 ms base RTT,
4 TCP flows saturating one direction):

| | idle | loaded median | loaded 95th pct | throughput |
|---|---|---|---|---|
| Download, no shaping | 20.1 ms | 366 ms | 420 ms | 19.1 Mbit |
| Download, autorate | 20.2 ms | 21.8 ms | 73.8 ms | 17.9 Mbit |
| Upload, no shaping | 20.1 ms | 364 ms | 420 ms | 19.0 Mbit |
| Upload, autorate | 20.2 ms | 42.4 ms | 81.6 ms | 18.7 Mbit |

`hifi-wifi bench` on the same link: latency increase under load **+306 ms (grade D) without
hifi-wifi, +2.9 ms (grade A+) with it**, at about 95% of throughput. The remaining spikes
(95th percentile) come from autorate probing slightly above the bottleneck before backing
off. A real Wi-Fi link adds its own variability; real-hardware numbers are what this beta
is for.

### 2. `hifi-wifi bench`: proof instead of promises

```
sudo hifi-wifi bench          # one run
sudo hifi-wifi bench --ab     # off, then on, side by side
```

It pings while idle, while downloading and while uploading at full speed (parallel `curl`
streams to Cloudflare's speed test by default). It reports median, 90th and 99th percentile
latency, jitter, loss and throughput, and a bufferbloat grade using the same bands as the
Waveform test (A+ under 5 ms increase, A under 30 ms, B under 60 ms, ...). Results are saved
as JSON in `/var/lib/hifi-wifi/bench/`.

Networks vary from minute to minute; run `--ab` a few times before drawing conclusions.

### 3. `hifi-wifi doctor`: what is actually limiting your Wi-Fi

Most stutter is the radio environment, and no software on the device can fix that. Doctor
says when that is the case and what to do:

- Signal strength (weak below about -70 dBm)
- On 2.4 GHz while a 5/6 GHz network with the same name is in range
- Low negotiated link rate
- Retransmission rate (live over 3 s when there is traffic) and packets lost after all retries
- Missed beacons
- How busy your channel is, including neighbors' networks
- Wi-Fi power save left on

Every warning comes with a concrete fix.

### 4. Game traffic priority, fixed

Game and game-streaming UDP (Steam game servers, Remote Play, Moonlight/Sunshine, and
anything in SteamOS/Bazzite game mode's `gamescope.slice`) is marked DSCP EF. The Linux Wi-Fi
stack then sends it through the voice/video queue, which wins airtime contention, and CAKE
puts it in its latency tin ahead of bulk uploads. Changes since v3.0:

- Works for IPv6, not only IPv4.
- Matches source **and** destination ports, so it works whether this device is the
  Moonlight client or the Sunshine host.
- No longer marks every app's UDP (that included browser QUIC uploads, which would have
  competed with your game in the priority queue).
- Applied once as one atomic `nft` ruleset for as long as the service runs.

This affects your device's own transmissions. It does not change how your router or ISP
treat traffic.

## Fixes

- **Slow Remote Play after waking from sleep until Wi-Fi is toggled**
  ([#23](https://github.com/doughty247/hifi-wifi/issues/23)). Drivers turn Wi-Fi power save
  back on when they resume, but hifi-wifi remembered it as "already off" and never re-applied
  it. It now re-applies its settings after resume, and every 30 s checks the driver's actual
  power save state and fixes it if something else changed it.
- **Slowdown after plugging in the charger** (#23). PCIe link power management was switched
  on the live Wi-Fi card on every AC plug/unplug, which some chips do not tolerate.
  `dynamic_aspm` is now off by default (the link is set once at startup), and link settings
  are only written when they actually differ.
- **Settings were re-applied to the network card on every network event.** Any link change,
  including virtual interfaces, re-ran the full system setup. Now only a carrier coming up on
  a managed adapter re-applies, and only the PCIe link and IRQ settings that a re-init resets.
- **Ethernet EEE is only changed when it differs.** Some drivers renegotiate the link on every
  EEE change, which drops the connection for a moment.
- **IRQ pinning showed "NOT FOUND"** ([#14](https://github.com/doughty247/hifi-wifi/issues/14)).
  Interrupts were found by guessing driver names in `/proc/interrupts`, which misses many
  drivers. They now come from the device's own sysfs entries. `status` reports what really
  happened: pinned, kernel-managed (the kernel places those vectors itself; nothing to fix),
  or N/A for USB adapters.
- **Ethernet is no longer capped.** v3.0 put CAKE at 60% of the link speed on connected
  Ethernet, limiting a docked gigabit connection to about 600 Mbit with no latency benefit.
  Wired connections are now handled by autorate like Wi-Fi.
- `hifi-wifi apply` no longer installs a static CAKE shaper that the daemon removed again a
  few seconds later.
- Reconnecting no longer force-applies CAKE when breathing CAKE is disabled.
- A panic during crash recovery can no longer trigger another recovery in a loop.
- `status` and `doctor` ignore autorate state left behind by a crashed daemon.
- Fixed loops reading `.bashrc` that could spin forever on a read error.
- `check-compat` now checks what 3.1 actually uses: tc, CAKE, IFB, ping, nft, iw, curl, BBR.
- Building no longer needs clang/LLVM or kernel headers.

## Removed (and why)

Earlier 3.1 development builds contained three features that review showed could not work.
They never shipped in a release:

- **"Zero-copy eBPF game bypass"**: it set packet priority on *arriving* packets. Arriving
  packets are not queued in a way that priority affects, so it changed nothing (and it was a
  tc classifier, not XDP). The real version of the idea is the DSCP marking above.
- **"Temporal packet duplication"**: it sent a second copy of each packet over the same
  radio at the same moment. Wi-Fi losses come in bursts, so both copies tend to be lost
  together, while the extra traffic uses airtime exactly when the link is weakest. Moonlight
  already has forward error correction for this.
- **TCP_INFO jitter telemetry**: it read socket stats by opening `/proc/<pid>/fd/N`, which
  the kernel refuses for sockets, so it never returned data. It also measured TCP, while game
  streams use UDP.

If you set `ebpf_bypass_enabled`, `multipath_*` or `[multipath]` in your config, they are
ignored. Leftover iptables rules from development builds are removed by `hifi-wifi revert`.

## Configuration

New `[autorate]` section (all optional; defaults shown):

```toml
[autorate]
mode = "busy"                  # "busy" (shape while busy), "always", or "off"
reflectors = ["1.1.1.1", "8.8.8.8", "9.9.9.9"]
ping_interval_ms = 300
idle_ping_interval_ms = 2000   # 0 disables idle probing
delay_threshold_ms = 15.0
min_download_mbit = 5.0
min_upload_mbit = 1.0
# max_download_mbit = 300.0    # default: governor.internet_*_mbit, else the link rate
# max_upload_mbit = 30.0
remember_rates = true
```

New in `[governor]`: `game_priority_enabled` and `game_priority_udp_ports`.
If you set `internet_download_mbit` / `internet_upload_mbit`, autorate uses them as upper
limits and starting points.

## Network usage

- Autorate sends small pings to its reflectors: about 3 per second while the link is busy,
  one every 2 seconds per reflector while idle. Set `mode = "off"` to disable.
- `bench` contacts `speed.cloudflare.com` only when you run it (change with `--download-url`
  and `--upload-url`).
- No telemetry.

## Known limitations

- **Not yet measured on real Wi-Fi hardware.** The numbers above come from simulation.
- Autorate cannot fix bloat caused by other devices saturating your network, or a weak or
  congested Wi-Fi link. `doctor` shows when that is the case.
- With a VPN as the default route, autorate does not shape (it only shapes physical
  interfaces it manages).
- Reflectors are IPv4. On an IPv6-only network autorate gets no latency samples and leaves
  the shaper open (the same as no shaping).
- Game traffic priority needs the `nft` command. Without it, `check-compat` warns and
  everything else still works.
- On first use on a new network, the first seconds of a large download can still be bloated
  while autorate finds the bottleneck. After that it remembers.
